C2/C3. ПЕРЕИСПОЛЬЗОВАТЬ ИНВЕНТАРНЫЕ CHARGES — НЕ ВЫЙДЕТ. НУЖЕН СВОЙ СЧЁТЧИК.

    Инвентарная инфраструктура (InventoryFeatureComponents.cs:24-27):
        public class InventoryCharges : IEntityComponent
        {
            public List<ReactiveVariable<int>> Value;
        }
    Это СПИСОК, индексируемый в лок-степе с массивом _consumables
    (InventoryItemConfig[]) — см. InventorySystem.OnInit:

        _chargesList = entity.InventoryCharges;
        _chargesList.Clear();
        // Рефил до капасити на каждом старте уровня. Схема расходников A:
        // количество не покупается и между забегами не хранится — покупается
        // вместимость, и забег всегда начинается полным.
        for (int i = 0; i < _consumables.Length; i++)
        {
            _chargesList.Add(new ReactiveVariable<int>(GetCapacityFor(_consumables[i])));
        }

    Чтобы засунуть туда слэш, он должен стать InventoryItemConfig. Последствия:
      - попадёт в ротацию колёсиком (HandleSwitchItem крутит по _consumables);
      - попадёт в инвентарный HUD (InventoryUIPresenter читает InventoryCharges
        по тому же индексу, строки 68-71, 87-91, 195-200);
      - будет «использоваться» через TryUseActiveItem по кнопке предмета,
        а слэш триггерится удержанием атаки — расход пришлось бы списывать
        МИМО TryUseActiveItem, то есть инфраструктура дала бы только хранение
        числа, а всю логику всё равно писать свою;
      - GetCapacityFor завязан на BagUpgradeConfig.TargetConsumableId — один
        апгрейд качает РОВНО ОДИН расходник, второй пришлось бы или дублировать
        конфиг, или ломать это правило.
    Итого: переиспользование даёт хранение int и забирает три чужих подсистемы.
    ДЕШЕВЛЕ СВОЁ.

    Форма своего (минимум типов):
      - компонент ChargedSlashCharges { ReactiveVariable<int> Value; }
        (один новый IEntityComponent -> потребует Tools/GenerateEntityAPI);
      - завод и рефилл — в EntitiesFactory.CreateHero рядом со строками 288-291,

E1. КОРНЕВОЙ АНЛОК.
    ShopItemConfigBase уже умеет бинарный товар: MaxTier => 1,
    TryGetCostForNextTier(0, out cost) => true, (1, ...) => false.
    Купленный анлок = GetTier(itemId) == 1. Ничего в базе менять не надо.
    Два варианта:
      (a) StatUpgradeConfig с одним тиром — врёт про полезную нагрузку
          (StatBonus не используется, а GetTierEffectText напечатает «+0% ...»),
          и TargetStat пришлось бы расширять несуществующим статом. ПЛОХО.
      (b) новый AbilityUnlockConfig : ShopItemConfigBase, поля: int _cost,
          string _effectText (или просто константа). MaxTier => 1.
          ~40 строк, ноль вранья. РЕКОМЕНДУЮ (b).

E2. ТРИ ВЕТКИ, ДВЕ НАГРУЗКИ НА ТИР.
    StatUpgradeConfig держит ОДИН StatBonus на тир:
        [Serializable] public class StatUpgradeTier
        {
            [field: SerializeField, Min(0)] public int Cost { get; private set; }
            [field: SerializeField, Range(0f,100f)] public float StatBonus { get; private set; }
        }
    и его TargetStat = { EvasionChance, DoubleAttackChance }, а текст эффекта
    жёстко в процентах ($"+{...}% {имя}"). Ни то, ни другое к слэшу не подходит.

    Варианты:
      (i)  расширить StatUpgradeTier вторым полем — заденет уже работающие
           уклонение и крит, у которых второе поле будет всегда пустым.
           Это ровно тот аргумент, которым в проекте обосновано разделение
           BagUpgradeConfig и ShurikenDamageUpgradeConfig:
           «у тиров разная размерность ... и общий конфиг заставил бы держать
            оба поля с одним всегда пустым». ПРОТИВОРЕЧИТ ПРЕЦЕДЕНТУ.
      (ii) один новый тип с enum-целью { Charges, Power, Reach } и тиром
           { Cost, BonusA, BonusB } — у ветки Charges BonusB всегда пуст,
           тот же упрёк, плюс безымянные A/B нечитаемы.
      (iii) по типу на ветку с осмысленными полями:
           ChargedSlashChargesUpgradeConfig  тир { Cost, ChargesBonus:int }
           ChargedSlashPowerUpgradeConfig    тир { Cost, DamageBonus, SpeedBonus }
           ChargedSlashReachUpgradeConfig    тир { Cost, LifeTimeBonus, HitboxScale }
           Три типа, каждый честен про свою нагрузку. РЕКОМЕНДУЮ (iii).
    Итого новых типов конфигов: 1 (анлок) + 3 (ветки) = 4.
    Это многовато, и если хочется ужаться — (ii) с внятными именами полей
    вместо A/B — приемлемый компромисс, но прецедент в проекте против него.

E3. КАТАЛОГ ПРИМЕТ — ПОДТВЕРЖДАЮ, И ЭТО ЕДИНСТВЕННЫЙ РАБОЧИЙ ПУТЬ.
    _items типизирован как List<ShopItemConfigBase>, любой наследник кладётся
    без правок презентера. Currency = SoulShard (<Currency>k__BackingField: 1)
    подхватится фильтром вкладок сам — проверено на прошлой итерации.
    ВАЖНО, ПОВТОРНО: ConfigsProviderService ключуется ТИПОМ —
        private readonly Dictionary<Type, object> _configs;
        public T GetConfig<T>() where T : class
    поэтому ДВА ассета одного типа через ResourcesConfigsLoader зарегистрировать
    НЕЛЬЗЯ (второй затрёт первый). При варианте (iii) все четыре типа разные,
    так что теоретически можно и через лоадер — но не надо: MainHeroFactory и
    ProjectileFactory всё равно должны ходить в каталог, чтобы список товаров
    остался в одном месте. Так уже сделано для стат-апгрейдов.
    Сейчас в ShopCatalogConfig.asset 4 записи, станет 8.

C:  использований СЕЙЧАС БЕЗЛИМИТ. Инвентарные charges переиспользовать НЕ СТОИТ:
    они список в лок-степе с _consumables, и вход туда тянет за собой ротацию

ПРЕРЕКВИЗИТ ВСЕЙ ЗАТЕИ: четыре числа слэша (damage 10, speed 15, lifeTime 2,
хитбокс 1x2 на префабе) сейчас захардкожены в теле фабрики. Пока их не вынесли
в ChargedSlashConfig, «база + бонус» вешать не на что.

ПОБОЧНОЕ НАБЛЮДЕНИЕ ПО ДИЗАЙНУ: дальность слэша = speed * lifeTime, поэтому
ветка «урон+скорость» неизбежно качает и дальность, пересекаясь с веткой
«дальность+радиус». Либо принять, либо перевести слэш на ограничение по
дистанции (как MaxFlyDistance у метательных).
