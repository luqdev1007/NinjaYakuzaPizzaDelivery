ГДЕ ТРОНУТ БОЕВОЙ ПУТЬ
--------------------------------------------------------------------------------
1. DoubleAttackSystem.IsChanceProceed — ролл прока двойного удара.
   Было:  return _random.Range(0f, 100f) <= percent;
   Стало: <=0 -> false; >=100 -> true; иначе _random.Range(0,100) < percent.
   Поведение при percent==0 меняется с «изредка да» на «никогда».
   При 0 < percent < 100 распределение то же, минус верхняя граница.

2. MainHeroFactory.ApplyStatBonus, ветка EvasionChance — читает боевой стат.
   entity.EvasionChanceModifiers.Add(new AdditiveStatModifier(bonus));
   Модификатор перманентный, В ДОПОЛНЕНИЕ к BaseEvasionChance, второго
   компонента не заводит. Кламп 0..100 делает EvasionChanceStatSynchronizerSystem.
   EvadedEvent на герое проверен, на месте (MainHeroFactory:76 в старой нумерации).

3. MainHeroFactory.ApplyStatBonus, ветка DoubleAttackChance — ПРЯМАЯ ЗАПИСЬ.
   entity.DoubleAttackChance.Value = Mathf.Clamp(value + bonus, 0, 100);
   Триплета Base/Modifiers/Synchronizer у крита нет, поэтому кламп ручной.

Порядок: ApplyPurchasedStatUpgrades зовётся ДО EntitiesLifeContext.Add, то есть
до entity.Initialize() -> OnInit систем. Синхронизатор уклонения делает первый
Recalculate уже с модификатором.

--------------------------------------------------------------------------------
SINGLE-WRITER-КОММЕНТАРИЙ У КРИТА — ПОДТВЕРЖДЕНИЕ
--------------------------------------------------------------------------------
MainHeroFactory.ApplyStatBonus, над строкой записи, дословно:

  // ВНИМАНИЕ, ВТОРОЙ ПИСАТЕЛЬ. DoubleAttackChance пишется здесь
  // (апгрейд) и в EntitiesFactory:278 (база из конфига). У крита
  // НЕТ триплета Base/Modifiers/Synchronizer, как у уклонения, —
  // значит нет и места, где значение собиралось бы из слагаемых,
  // и порядок записей определяет результат. Сейчас это держится
  // ровно потому, что писателей два и они упорядочены: фабрика
  // сущности залила базу, мы прибавляем поверх.
  //
  // ПОЯВИТСЯ ТРЕТИЙ ПИСАТЕЛЬ (бафф, дебафф, ещё один товар) —
  // строить триплет, а не дописывать сюда: иначе разъедется
  // молча, как уже разъезжались CompletedLevels у двух сервисов
  // и LootCollectRange у двух Add'ов в этой самой фабрике.
  //
  // Кламп здесь ручной по той же причине — синхронизатора,
  // который сделал бы это за нас, не существует.

ПОЧЕМУ КОНФИГИ ЧЕРЕЗ ShopCatalogConfig, А НЕ ЧЕРЕЗ ResourcesConfigsLoader
--------------------------------------------------------------------------------
ConfigsProviderService ключуется ТИПОМ (Dictionary<Type, object>), а оба
стат-апгрейда — один и тот же тип StatUpgradeConfig. Регистрация второго
затёрла бы первый. MainHeroFactory берёт их из каталога и фильтрует
`as StatUpgradeConfig`. Каталог заодно остаётся единственным списком того,
что продаётся.
